# Roadmap

---

## 1. Что уже сделано

Analyzer умеет:

- обходить активные участки по расписанию;
- собирать детекции техники за окно времени;
- агрегировать их по классам (максимум одновременного присутствия);
- проверять правила `required` / `unexpected` / `allowed`;
- проверять молчащие камеры (`no_data`);
- проверять «техника есть, этапов нет» (`unplanned_activity`);
- проверять не-наблюдаемые виды работ (`not_observable`);
- учитывать grace-периоды на перегонку техники;
- вести жизненный цикл отклонений (открытие, обновление, закрытие);
- прикладывать кадры-доказательства;
- писать журнал изменений через триггер `deviation_on_change`.


---

## 2. Продуктовые решения

Ниже — решения, которые определяют следующий слой логики.

### 2.1. Точное время этапов

**Решение.** Если заказчик указал точное время начала и окончания
этапа — работаем в часах. Если не указал — считаем «этап с 00:00»
по московскому времени.

**Что это значит для БД.**
В `plan_task` добавляются опциональные поля:

- `start_at timestamptz` — точное время начала;
- `end_at timestamptz` — точное время окончания.

Поля `start_date` и `end_date` типа `date` остаются. Логика выбора:

- если `start_at` заполнено — используем его;
- иначе — `start_date` в 00:00 MSK.

Это сохраняет обратную совместимость: старые этапы продолжают
работать, новые могут быть точными.

**Что это значит для Analyzer.**
Меняется ровно одно место — `grace.py`, где считается «начало
этапа». Вместо `start_of_day_msk(task.start_date)` будет
`task.start_at or start_of_day_msk(task.start_date)`. Вся остальная
логика не меняется.

**Что это значит для API.**
API должен принимать `start_at` / `end_at` опционально.
Если заказчик не знает точное время — он их не передаёт, и
поведение системы остаётся прежним.

**Открытые вопросы.**

- Что если `start_at` заполнено, а `start_date` — нет? (По схеме
  `start_date` сейчас `NOT NULL`. Возможно, стоит разрешить `NULL`,
  если есть `start_at`.)

---

### 2.2. Календарное отставание

**Решение.** Пока считаем только календарное отставание —
насколько текущая дата ушла за плановую дату окончания этапа.
Прогноз завершения не делаем.

**Что это значит.**
Для каждого активного этапа:

- `today < start_at` → этап ещё не начался (`planned`);
- `start_at ≤ today ≤ end_at` → этап идёт (`on_track`);
- `today > end_at` и этап не закрыт → этап просрочен на
  `today − end_at`. Это и есть «отставание».

Величина отставания считается в тех же единицах, что и точность
плана: если время известно — в часах, если нет — в днях.

**Что это значит для БД.**
Нужна вычисляемая сущность — статус этапа относительно сроков.
Логично оформить отдельной SQL-функцией:

schedule_status(plan_task_id, as_of) → planned | on_track | overdue | completed | unknown

Функция не дублирует `stage_status` (тот про фактические
отклонения), а дополняет её: `stage_status` отвечает «что с
техникой», `schedule_status` — «что со сроками».

**Что это значит для Analyzer.**
Analyzer ничего не пишет в БД по этому поводу. Он может
**вычислять** и логировать отставание, но состояние хранит
SQL-функция на лету.

**Что это значит для Front.**
Front показывает по каждому этапу две вещи отдельно:

- состояние по технике (`ok` / `violation` / `not_observable`);
- состояние по срокам (`on_track` / `overdue` с числом часов/дней).

Это разделение важно: этап может быть «в графике, но с нарушением
правил» и наоборот.

**Открытые вопросы.**

- Отставание считать от `end_at` или от `end_date`? 

- Нужно ли «отставание» показывать как `deviation`, или это
  отдельная сущность?

### 2.3. Автоматическое закрытие этапов

**Решение.** Analyzer сам определяет, что этап завершён, и
**предлагает** его закрыть. Если пользователь подтверждает —
этап закрывается. Если не подтверждает — этап возвращается в
активное состояние. Если пользователь молчит N часов —
Analyzer закрывает этап сам.

**Что это значит.**
Вводится новая роль Analyzer: не только «проверяет правила», но и
«предлагает решения по состоянию плана».

**Критерий «этап завершён».**
Предлагается консервативный:

1. `end_at` этапа прошёл (`today > end_at`);
2. required-техника не наблюдается N итераций подряд;
3. открытых отклонений уровня `violation` по этапу нет.

Только все три условия вместе. Если хотя бы одно не выполнено —
этап считается активным.

**Что это значит для БД.**
Нужны поля и, скорее всего, отдельная таблица:

- в `plan_task` — поле `suggested_closed_at timestamptz` —
  когда Analyzer предложил закрыть;
- отдельная таблица `plan_task_status_history` — журнал
  переходов: `opened`, `suggested_close`, `closed`, `reopened`,
  `cancelled_suggestion`. По аналогии с `deviation_history`.
- поле `closed_by` в `plan_task` (`user` / `system`) — кто
  закрыл. Сейчас есть только `closed_at`.

**Что это значит для Analyzer.**
Логика такая:

1. Если этап удовлетворяет критерию завершённости и ещё не закрыт —
   поставить `suggested_closed_at = now()`.
2. Если `suggested_closed_at` стоит и прошло N часов без реакции —
   закрыть этап (`closed_at = now()`, `closed_by = 'system'`).
3. Если пользователь через API подтвердил — закрыть сразу.
4. Если пользователь через API отклонил — снять
   `suggested_closed_at`, записать отказ в историю, и **не
   предлагать снова** в течение M часов (или до изменения
   ситуации: техника появилась, нарушение открылось и т.д.).

Analyzer **не блокируется** ожиданием ответа пользователя. Он
продолжает обходить участки по своему графику, этап просто
находится в состоянии «предложено закрыть».

**Что это значит для API.**
Появляются эндпоинты:

- `POST /plan_tasks/{id}/confirm_close` — пользователь подтверждает;
- `POST /plan_tasks/{id}/reject_close` — пользователь отклоняет;
- `GET /plan_tasks?status=suggested_close` — список предложенных
  закрытий.

**Что это значит для Front.**
Страница или виджет «Предложенные закрытия» — список этапов, по
которым Analyzer ждёт решения. С кнопками «Подтвердить» /
«Отклонить».

**Открытые вопросы.**

- Порог молчания N — сколько часов? Предложение: 24 часа.
- Порог M для «не предлагать снова» — сколько? Предложение:
  12 часов, либо до изменения ситуации.
- Обратимо ли auto-close? Если пользователь через неделю скажет
  «этап ещё шёл» — можно ли «открыть обратно»? Предложение: да,
  через API, с записью в историю.
- Что если auto-close сработал, а следующий этап ещё не начался?
  Кто виноват — Analyzer, заказчик, реальность?

### 2.4. Накладка этапов — всегда отклонение

**Решение.** Если этап A ещё не закрыт, а этап B уже начался —
это всегда отклонение.

**Что это значит.**
Нужен новый тип отклонения — `stage_overlap`. Проверяется на
уровне **набора** активных этапов участка, а не одного этапа.

Логика:

1. Взять все активные этапы участка.
2. Если два этапа пересекаются по датам/времени и оба ещё не
   закрыты — создать `stage_overlap`.
3. Severity — `warning` (обсудить: может, `critical`).
4. В сообщении указать оба этапа и величину пересечения.

**Что это значит для БД.**
В `deviation.type` добавляется `stage_overlap`. В `deviation_refs`
CHECK-констрейнте появляется новая ветка: для `stage_overlap`
`plan_task_id IS NULL`, потому что отклонение не про один этап,
а про пару.

Вопрос: как ссылаться на два этапа сразу? Варианты:

- ссылаться на «второй» этап (тот, что начался позже);
- ввести отдельную таблицу связи `deviation_plan_tasks`;
- хранить оба id в `message` (некрасиво).

Предложение: ссылаться на «второй» этап (`plan_task_id` = этап B),
а этап A упоминать в `message`. Этого достаточно для MVP.

**Что это значит для Analyzer.**
Новый модуль `schedule.py` в `services/`, который проверяет
расписание участка как целое. Он не заменяет `rules.py`, а
дополняет.

**Открытые вопросы.**

- Бывают ли у заказчика **легальные** параллельные этапы? Если да —
  нужен флаг «разрешено пересекаться» на этапе.
- Как считать «начался» этап B? По `start_at`, по `start_date`, или
  по фактическому появлению техники?
- Severity — `warning` или `critical`? Предложение: `warning`,
  чтобы не перегружать критикой.

---

### 2.5. Активность техники — работает или стоит

**Решение.** Техника, которая стоит без движения, — не работает.
Её присутствие не считается выполнением работ.

**Что это значит.**
Нужен **отдельный слой** — трекинг техники между кадрами. Это не
задача Analyzer в текущем виде: Analyzer работает с агрегатами
(«сколько каких классов»), а трекинг требует поштучного
сопоставления объектов между кадрами.

**Что нужно.**

1. Для каждого класса и каждой камеры — сопоставлять bbox между
   соседними кадрами.
2. Для каждой пары «объект на кадре N» — «объект на кадре N+1»
   считать смещение.
3. Если смещение больше порога — «в работе», иначе — «стоит».
4. Пропуски на 2–3 кадра не должны разрывать трек.

**Где это может жить.**

- **Отдельный сервис Activity** — чище по ответственности, дороже
  по инфраструктуре.
- **Analyzer с расширенным окном** — временное решение, плохо
  масштабируется.


**Открытые вопросы.**

- Порог смещения в пикселях — какой?
- Заказчику нужно «какие конкретно машины работают» или
  «сколько в целом»? Скорее всего какие конкретно.
- Стоит ли учитывать «простой на обед/пересменку» как норму?

---

### 2.6. Прогноз завершения — не делаем

**Решение.** Прогноза сроков завершения этапов не делаем.
Показываем только текущее отставание.

**Что это значит.**
Отпадает целый слой аналитики: тренды, темп работ, сезонность,
выходные. Это сильно упрощает и ускоряет разработку.

Если заказчик вернётся к вопросу — можно добавить позже, когда
накопится история за несколько месяцев.

## 3. Этапы разработки

Разбито по возрастанию сложности. Каждый этап самостоятелен и
даёт заказчику осязаемый результат.

### Этап 1. MVP Analyzer — сделан

Всё, что перечислено в разделе 1.

### Этап 2. Календарные проверки

Добавляет:

- `plan_task.start_at` / `end_at` (timestamptz, nullable) — задача
  по БД;
- SQL-функция `schedule_status(plan_task_id, as_of)`;
- проверка `stage_overdue` — этап просрочен;
- проверка `stage_overlap` — накладка A/B;
- поддержка точного времени в grace-периодах.

Не добавляет auto-close, трекинг, прогноз.

Результат для заказчика: видит, какие этапы просрочены и на
сколько, видит накладки.

### Этап 3. Автоматическое закрытие этапов

Добавляет:

- поле `suggested_closed_at` в `plan_task`;
- поле `closed_by` в `plan_task`;
- таблицу `plan_task_status_history`;
- логику предложения закрытия в Analyzer;
- эндпоинты `confirm_close` / `reject_close` в API;
- виджет «Предложенные закрытия» во Front.

Результат для заказчика: этапы закрываются автоматически, если
Analyzer уверен и заказчик не возражает.

### Этап 4. Активность техники

Добавляет:

- трекинг bbox между кадрами;
- Проверка техника работает или стоит.

Результат для заказчика: видит, что техника не просто стоит на
площадке, а действительно работает.

## 4. Открытые вопросы для команды и заказчика

Список того, что нужно обсудить до начала каждого этапа.

**Для команды по БД:**

1. Добавляем ли `plan_task.start_at` / `end_at`? Обязательно ли
   заполнять оба, или можно одно?
2. Меняем ли `start_date` на nullable, если есть `start_at`?
3. Как оформлять `schedule_status` — отдельной SQL-функцией или
   вычислять в приложении?
4. Добавляем ли `plan_task.closed_by`?
5. Нужна ли `plan_task_status_history` или хватит полей
   `closed_at` / `reopened_at`?
6. Расширяем ли `deviation.type` — добавляем `stage_overdue`,
   `stage_overlap`?
7. Как ссылаться на пару этапов в `deviation` при накладке?

---

## 5. Что сознательно не делаем

Чтобы не расползалось:

- **прогноз сроков завершения** — не делаем, пока заказчик не
  попросит;
- **учёт выходных и праздников** — не делаем, календарное
  отставание считается от `end_at` буквально;
- **автоматическое изменение плана** — не делаем, планом управляет
  заказчик, а Analyzer только фиксирует факты;
